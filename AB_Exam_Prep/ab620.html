How to study this exam

For every requirement, explain which component reasons, which performs fixed work, whose identity accesses data, and how you detect an incorrect result. Learn decisions, not menu positions.

  1. Use one scenario. Build the fictional Northwind Service Desk with synthetic policy, request status, and human review. Exclude real personal data and secrets.
  2. Baseline all nine groups. Try each drill, classify misses, and treat unexplained guesses as gaps.
  3. Prioritize integration. Domain 2 has the largest weight, but identity and flow fundamentals still govern its design.
  4. Retrieve, then explain. Close a group, reconstruct its decision table, and explain why the closest alternative fails.
  5. Experiment carefully. Change one source, prompt, mapping, or description at a time; rerun fixed cases under a known identity.
  6. Rehearse operations. Exercise failures and denied access, inspect results, and package dependencies rather than rebuilding by hand.

The labs use tiny synthetic datasets and are not official exam lab simulations. Their examples and success criteria are teaching choices. Practice supports preparation but cannot predict the exam's undisclosed question mix or scoring formula.

Exam tip

Underline the governing constraint: existing API, no API, independent ALM, user-specific permissions, live data, deterministic order, semantic correctness, or environment-specific configuration. The constraint usually eliminates more distractors than product names do.

Lab environment setup

Use a work or school account with approved access to a nonproduction Copilot Studio environment. A Power Apps developer environment is useful for Dataverse and solutions but does not, by itself, grant every Copilot Studio capability. Tenant policies, region, licensing, available capacity, and administrator permissions can affect what you can try.

  • Authoring experience: use topics, agent flows, tools, and solution-aware agents. Current docs call many of these the standard harness. New workflow authoring is not the established agent-flow format.
  • Trial boundary: a trial permits agent creation and test chat, not agent publishing. Channel deployment and pipelines require appropriate rights.
  • Synthetic knowledge: create a text document: “Northwind service policy. Standard support runs Monday through Friday. Requests need an asset ID and problem description. This agent cannot authorize purchases.” Label policy versions explicitly.
  • Data fixture: optionally create a Dataverse Service Requests table with Request ID, Asset ID, Status, and Summary. Use NW-100, DEMO-LAPTOP-1, and Awaiting review. Otherwise return fixed simulated flow outputs.
  • Credentials: use supported connection dialogs. Exclude passwords, keys, tokens, and actual connection strings from prompts, knowledge, cards, screenshots, and exports.
  • Optional dependencies: Search, Foundry, Application Insights, Fabric, MCP, computer-use machines, and pipelines need additional access/resources. Core exercises offer simulations; these do not verify external integrations.
  • Cleanup: remove obsolete fixtures/connections, stop metered resources, and apply retention rules to test sets, screenshots, transcripts, and telemetry.

Use Get access to Copilot Studio to verify trial restrictions, and security and governance guidance to identify administrator-controlled boundaries. Ask your environment administrator about unavailable features rather than bypassing policy.

Domain 1 — Plan and configure agent solutions (30–35%)

Design the trust boundaries first, then implement a narrow process with flows and topics. Connect architecture to concrete authoring decisions: audience, channels, credentials, data handling, variable contracts, and predictable responses.

1.1 Plan an agent solution

Plan the outcome and authority boundary before building: Northwind may explain policy, retrieve status, or prepare a request, but cannot approve a purchase. Each capability needs proportionate controls.

Turn requirements into an integration plan

Inventory systems of record, APIs, connectors, owners, freshness, and failures. Knowledge explains policy; the live service determines transaction state. A citation never proves a write succeeded.

For every reusable component, document purpose, typed inputs/outputs, identity, failures, owner, and dependencies. Prefer stable identifiers and status fields over transcripts so multiple topics can share the contract.

RequirementPreferWhy not the nearby alternative?
Explain an approved service policyMaintained knowledge with citations.A write connector adds risk and does not improve the evidence.
Read current request statusA connector/API tool against the system of record.A copied policy or static export is not a live transaction lookup.
Complete fixed validation and routing stepsAn agent flow or explicit topic sequence.Free-form orchestration alone does not enforce a mandatory sequence.
Serve employees in a supported Microsoft channelMicrosoft authentication plus source permissions and channel validation.A Teams account does not grant every downstream permission.
Serve anonymous public FAQ readersApproved public knowledge and intentionally limited tools.Maker access to private sources must not become public access.
Reuse capabilities across independent teamsA governed reusable integration or connected agent with a clear contract.Copying prompts and credentials creates drift and scattered ownership.

Identity, audience, and channels are one design decision

Separate maker, conversation user, and connection identities. Chat sign-in establishes identity, not downstream authorization. Inspect each tool connection and enforce permissions in its service.

Microsoft authentication serves supported Microsoft channels; other channels can require manual configuration. Deployment changes require publishing. Test cards, citations, accessible text, and escalation on the actual channel.

Responsible AI and governance belong in the plan

Turn fairness, reliability and safety, privacy and security, inclusiveness, transparency, and accountability into controls: disclose AI, minimize data, offer escalation, test exclusions, and assign accountable owners.

Use data policies, environment separation, roles, and service authorization. Prompts cannot replace them. Treat retrieved instructions and tool text as untrusted data, never permission to expand authority.

Lab 1.1 — Design two audiences safely
  1. Create a Northwind Service Desk agent in your nonproduction environment. Give it a narrow purpose: explain the synthetic service policy and prepare, but not approve, a service request.
  2. Add the synthetic policy document. Write instructions to explain uncertainty, use approved sources, and avoid claiming submission without a successful tool result.
  3. Record a two-column design for an employee agent and a public FAQ agent: authentication, permitted knowledge, permitted actions, escalation, and target channel. Do not enable anonymous access to private data.
  4. Review available authentication and connection settings without weakening tenant policy. Note which settings are administrator-controlled and which require publishing to affect deployment.
  5. In test chat, ask for the service policy, an unknown customer's request, and permission to approve a purchase. Compare the responses with your boundaries.

Success check: you can identify the identity for every planned data access, separate public from employee content, and show that the agent does not claim unauthorized approval. Channel publishing remains an optional licensed exercise.

Exam tip

If a question changes the audience from internal employees to external customers, reassess identity, source exposure, channels, and tool credentials together. Changing the greeting is not a security design.

Trap

“The agent requires sign-in” does not mean “all tools automatically run with least-privileged user access.” Review the connection and enforce access at the underlying system.

Did you know?

Power Platform data policies can control HTTP requests and publication channels as well as connectors. A blocked integration can therefore be a governance outcome rather than a malformed prompt.

1.2 Create and monitor agent flows in Copilot Studio

A flow defines a trigger, actions, branches, and returned outputs. Orchestration chooses the capability; the flow owns mandatory steps. Use it for explicit validation and routing, not free-form process invention.

Rule-based flow structure can contain variable AI outputs and changing service data. It does not guarantee identical content or safe retries of writes.

Design inputs and outputs first

A callable flow needs When an agent calls the flow, Respond to the agent, publication, and real-time response configuration. Keep synchronous work short; separate long human approvals.

Example contract: text requestId input; Boolean found and text status/message outputs. Preserve text identifiers and distinguish not found, denied, and unavailable.

SituationPatternCheck
Short lookup during chatAgent-callable flow with mapped input and outputs.Bound the work and return relevant fields only.
Approval may take hoursCreate a pending request, acknowledge it, and complete approval separately.Queued does not mean approved.
Negative business outcomeCondition and explicit business-status output.Not eligible is different from connector failure.
Transient dependency failureBounded retry where appropriate, then controlled recovery.Check retry safety and prevent duplicate writes.
Common recovery across related stepsScopes and run-after handling supported by the designer.Cover failure, timeout, and skipped paths.
False ticket confirmationInspect run inputs, action outputs, then topic mapping.Prove the record exists before confirming creation.

Human in the loop is a process state

Human-in-the-loop approval needs a reviewer, rejection route, timeout/escalation, and recorded outcome. A conversational confirmation does not replace manager approval or service permissions.

For long approvals, create a durable pending record and return its ID promptly. A separate process records the human decision; later lookup reports the outcome without holding chat open.

Monitor execution, not just the final sentence

Flow checker detects configuration defects, not business correctness. Inspect trigger input, connection identity, branch, timing, outputs, and recovery actions. Correlate with a nonsecret request ID; minimize logged payloads.

Validate inputs before calling. Investigate permission failures instead of retrying endlessly. A remote write may succeed despite a lost response: use service-supported duplicate prevention when retries could repeat it.

Lab 1.2 — Build a typed status flow and review boundary
  1. Create an agent flow with an agent-call trigger. Add a text input requestId and a response action returning Boolean found plus text status and message outputs.
  2. Add a condition for NW-100. Return found=true and status=Awaiting review for that synthetic ID; return found=false for another ID. Fixed values are sufficient if Dataverse is unavailable.
  3. Check and publish the flow if permitted, then add it to a test topic. Map the topic ID to the trigger input and the returned values to topic variables.
  4. Test NW-100, an unknown ID, and an empty value. Add validation for the empty value. Inspect each available test or run record and its branch.
  5. Add a “prepare for review” branch returning Pending human review without a consequential write. If an approved Approvals connection is available, implement the separate approval process against synthetic data; otherwise label it simulated.
  6. With an available test connector, induce a safe failure using a nonexistent synthetic record. Configure recovery and confirm it returns failure rather than success. Do not damage real credentials to induce an error.

Success check: valid, missing, and unknown inputs are distinguishable; failed actions never produce false completion; human review stays pending until an actual decision. A simulation proves mappings, not external connector behavior.

Exam tip

If a flow is absent from available tools, check its trigger, response action, publication state, and real-time configuration. For incorrect output, inspect parameter mappings before rewriting the entire prompt.

Trap

A green run can still have the wrong business outcome. A not-found branch may be technically successful, while a swallowed connector error can leave misleading output. Test the returned contract.

Did you know?

Saved flow versions are recorded in Dataverse. Version history helps separate the draft you are editing from the previously published version when investigating a regression.

1.3 Configure topics

A topic owns a bounded conversation: questions, typed values, conditions, tools, and responses. Use explicit sequencing for mandatory validation even when generative orchestration selects the topic.

Separate data, generation, and presentation

Separate authoritative facts from generation and display. APIs/flows retrieve or change records; prompts transform supplied context; generative answers retrieves knowledge; messages/cards present results.

Specify task, inputs, output structure, uncertainty behavior, and untrusted-data handling. Validate generated structured output before using it. Asking for JSON is not schema validation.

Need inside a topicUseBoundary
Validation followed by a lookupQuestion/condition nodes, then a mapped flow or connector.Outputs need the expected type and business meaning.
Summarize supplied incident factsA custom prompt with named inputs and output expectations.It does not automatically fetch missing enterprise facts.
Answer policy with evidenceA generative answers node scoped to approved sources.Source selection and authentication determine evidence.
Use a custom retrieval serviceRetrieve with a tool/HTTP call and supply supported custom context.Preserve title and location for citation; do not treat citations as tool inputs.
Call REST in a fixed sequenceSend HTTP request with method, schema, and error handling.This differs from an OpenAPI-described REST tool.
Collect several structured inputsInteractive Adaptive Card with submit action and mapped outputs.Test the host and stale submissions.
Display noninteractive informationMessage node, optionally with a display card.An input card can unnecessarily block conversation.

Variable scope and type are part of the contract

Use topic variables locally, explicit inputs/outputs for reusable topics, globals for conversation-wide state, system variables for runtime context, and environment variables for deployable configuration.

Use Power Fx to validate and transform values. Preserve IDs such as “00123” as text. Generated sample schemas do not prove real responses handle nulls, missing fields, or error payloads.

Control knowledge scope and HTTP recovery

Search only selected sources replaces the node's agent-level source set; it does not automatically fall back to other sources. Custom Data and certain older integrations use Classic data settings.

For custom knowledge, retrieve permitted passages with source titles and URLs, then supply supported custom context. Preserve provenance and keep retrieved content separate from trusted instructions.

Configure HTTP method, headers, body, and schema. Default failure invokes On Error; Continue on error stores status/body for explicit branching. Check those values and never embed literal credentials.

Interactive cards need submit actions, stable input IDs, correct output schemas, and host testing. Guard stale/repeated submissions. Card validation improves usability; service validation protects transactions.

Lab 1.3 — Build a guided request-status topic
  1. Create a topic that asks for a synthetic request ID, stores it as text, and rejects blank input with a corrective question.
  2. Call the Lab 1.2 flow and map requestId, found, status, and message. Branch on found before showing formatted status; use an honest not-found response on the other branch.
  3. Add an interactive Adaptive Card collecting asset ID and problem description with a submit button. Inspect its generated schema and returned variables in test chat.
  4. Add a generative answers node in a policy branch and scope it to the synthetic document. Ask an in-scope policy question and an unsupported purchasing question.
  5. If prompts are enabled, summarize only the submitted problem description using a custom prompt. Compare summary with source; do not use it as approval.
  6. If an approved test API exists, add a read-only HTTP request, map a sample JSON response, and exercise an error branch. Otherwise use a topic record variable and explicitly mark the HTTP portion untested.

Success check: the topic preserves text IDs, maps outputs, collects card fields, and separates sourced answers from live status and generated summaries. Failed lookups do not produce invented status.

Exam tip

Retrieval and synthesis suggests generative answers; transforming supplied text suggests a prompt; a fixed API call suggests HTTP/tool invocation; multiple structured user inputs often suggest an interactive card.

Trap

A card that renders in test chat can behave differently in Teams or a website. Continue on error also does not make an HTTP request successful: it transfers responsibility to your topic logic.

Did you know?

You can correct an Adaptive Card's generated output variables by editing its schema. If a form value is visible but missing or mistyped later, inspect the schema before blaming orchestration.

Domain 2 — Integrate and extend agents in Copilot Studio (40–45%)

Choose the integration by its job: retrieve enterprise knowledge, perform an operation, delegate to another agent, or use Azure-hosted retrieval, models, and telemetry. Similar names do not imply interchangeable security or runtime behavior.

2.1 Connect to enterprise knowledge sources

Grounding retrieves relevant, permitted evidence. Choose sources by location, freshness, permissions, indexing ownership, and answer-versus-action requirements. Connection readiness alone does not establish quality.

Three integration families, three different jobs

Copilot connectors: the indexed enterprise pattern uses Microsoft Search. Plan ingestion freshness, identity mapping, and source access; validate permitted and denied users.

Power Platform connectors: API wrappers for actions and supported knowledge. Real-time knowledge is Preview; metadata is indexed, while runtime queries use user authentication against the source.

Azure AI Search: choose when your team owns retrieval preparation, vectorization, and ranking. Supported integrated vectorization and semantic ranking retrieve evidence; the model generates from it.

RequirementCandidateVerify before choosing
Reuse enterprise content already indexed for Microsoft SearchCopilot connector knowledge.Connector availability, crawl freshness, permission mapping, and user authentication.
Query supported business data at runtimePower Platform real-time knowledge connector (Preview).Supported tables, user connection, source permissions, and service latency.
Own chunking, vector retrieval, and rankingAzure AI Search knowledge connection.Index readiness, embedding compatibility, citation URL fields, and access design.
Read or update one specific requestA connector/API tool.Typed contract and authoritative result; knowledge retrieval is not a write API.
Answer a small approved static policyUploaded synthetic policy for the lab.Version ownership and intended exposure; upload does not reproduce original repository ACLs.

Build a retrieval diagnosis ladder

  1. Availability: Is the source connected and ready? Can the intended test user reach it?
  2. Coverage: Does the source actually contain an explicit answer? A generated FAQ cannot create missing policy.
  3. Retrieval: Does a representative query return the right passage rather than an obsolete or similarly named document?
  4. Generation: Does the answer preserve conditions and cite evidence without adding an unsupported promise?
  5. Authorization: Can a lower-privileged persona retrieve content they should not see? A successful administrator test is insufficient.

Search citations need a document URL field and an accessible destination. A visible citation does not prove security-trimmed retrieval: separately inspect connection identity and data access.

Documentation caution: the Search article mixes key-based instructions, an Entra-based caution, and several authentication choices. Use the supported formal connection for your tenant; validate current guidance with your administrator.

Lab 2.1 — Compare retrieval quality and source boundaries
  1. Add the synthetic Northwind policy as knowledge and wait until it is ready. Ask a direct policy question and a paraphrase; inspect cited material.
  2. Create a second synthetic document with an explicitly older policy version. Ask a question whose answer differs between versions. Inspect whether the source selection and answer respect the intended current version.
  3. Remove the obsolete source or scope a topic to only the approved source. Rerun the same questions and compare evidence, not just fluency.
  4. If approved SharePoint or a supported real-time knowledge connector is available, add a small synthetic source and test with a permitted account. If a second test persona is available, verify the denied-access case as well.
  5. If an Azure AI Search sandbox is available, connect an already prepared vector index with non-sensitive documents and citation URLs through the supported data connection. Otherwise write the expected index fields and access checks as a design exercise; do not claim that Search was tested.

Success check: you can explain indexed versus runtime retrieval, show a correct cited answer, and identify which permission and freshness checks remain unverified when optional services or a second persona are unavailable.

Exam tip

“Indexed enterprise content,” “runtime query against the source,” and “custom vector index” point to different patterns. Also distinguish adding a connector as knowledge from adding one of its operations as a tool.

Trap

Knowledge cannot approve or update a transaction. Conversely, a connector being available as an action does not guarantee that it is supported by the real-time knowledge experience.

Did you know?

In the documented real-time knowledge connector pattern, Microsoft indexes source metadata while the actual request executes at runtime against the enterprise system. Metadata indexing and document-content indexing are different architectures.

2.2 Add tools to agents

Tools need precise selection metadata, narrow inputs/outputs, least-privileged credentials, and reliable outcomes. Good descriptions do not compensate for excessive permissions or unvalidated operations.

Choose the narrowest reliable integration

Prefer a connector/API over GUI automation when available. Reuse an approved custom connector operation; verify its environment, connection identity, schema, and policy instead of rebuilding it.

The direct REST API tool experience is Preview. Configure OpenAPI, authentication, descriptions, and selected operations. Expose only necessary capabilities; this differs from a topic's raw HTTP node.

MCP exposes server tools to the agent. Configure trust, authentication, and supported Streamable transport; older SSE is not supported. Metadata guides selection but does not enforce access.

Computer use operates a Windows GUI when no suitable API exists. It requires generative orchestration plus machine, credential, screen-state, supervision, and trace-review planning.

ScenarioPreferOperational risk to address

Service exposes a documented REST APICustom connector or supported REST API tool experience (Preview).OpenAPI quality, selected operations, authentication, and error semantics.

Legacy application has only a GUIComputer use with constrained access and supervision.Machine readiness, account scope, navigation errors, and replay evidence.

Describe selection and validate execution separately

Name the outcome precisely: “Look up Northwind request status by request ID.” Explain when to use it, required inputs, exclusions, and side effects. Map known facts instead of inventing identifiers.

Test success, denied access, missing authentication, empty data, and malformed responses. Treat tool output as data, not authorization. Inspect actual invocations as well as final prose.

Configure and monitor computer use

For computer use, select machine and connection, define task inputs, restrict websites/apps, and configure stored credentials securely. Maker-provided credentials can expose the maker's machine access to agent users.

Inspect computer-use screenshots, step logs, and actual destination state. Allowlisting restricts interactions, not all navigation or network access. Human supervision does not replace application authorization or business approval.

Lab 2.2 — Prove tool selection before adding risk
  1. Add the Lab 1.2 read-only flow as a tool. Give it a precise name and description, including the required request ID and the fact that it does not approve or modify requests.
  2. Test “What is NW-100's status?” and “What is the support policy?” Confirm the first uses the lookup and the second uses knowledge rather than an unrelated tool.
  3. If an approved custom connector exists, add one read-only operation and map a synthetic input. Compare its connection identity and returned schema with the flow contract.
  4. With an approved MCP server, connect through the supported onboarding experience, select a harmless lookup, and inspect its invocation. Without a server, compare its documented tool schema with your flow inputs as a contract exercise.
  5. If computer use and a nonproduction machine are available, configure a tool limited to reading a synthetic field in an approved test app. Set access boundaries, test it, and inspect run evidence. Otherwise write the machine, credential, supervision, and verification checklist without executing GUI automation.

Success check: you can demonstrate correct selection and mappings in the core agent, explain why an API is preferable to screen automation when available, and distinguish implemented tools from optional integrations you have only designed.

Exam tip

MCP exposes tools; A2A delegates to agents. An OpenAPI file describes API operations; it does not turn a service into an independently reasoning agent. Computer use is the GUI option, not the default replacement for an existing API.

Trap

“Read-only instructions” do not revoke write permissions held by a connection. Enforce least privilege in the service or machine account and expose only the operations the scenario needs.

Did you know?

Copilot Studio's MCP connection supports authentication choices including API key and OAuth 2.0. Using a standardized protocol does not mean the server is anonymous or that authentication is automatic.

2.3 Configure multi-agent collaboration from Copilot Studio

Multi-agent design delegates bounded tasks to specialists. Split when ownership, reuse, isolation, or measured routing problems justify extra hops; one well-scoped agent may be sufficient.

Choose a boundary that matches ownership

A child agent groups behavior locally without independent deployment/authentication. A connected agent supports separate ownership, settings, reuse, and ALM. Neither implies shared credentials or state.

A Northwind policy helper may be a child; a benefits specialist serving several teams may be connected. Do not add a separately orchestrated agent for every small API operation.

RequirementUseReason
Group one team's related behavior without independent publishingChild agent.Lightweight local modularity within the main agent.
Reuse an independently maintained Copilot Studio specialistConnected existing Copilot Studio agent.Separate ownership and lifecycle boundary.
Delegate to a specialist hosted in Microsoft FoundryFoundry-agent connection (Preview).The target agent supplies its own reasoning and tools; validate protocol prerequisites.
Ask analytical questions over governed Fabric dataFabric data-agent connection (Preview).Use the specialist data agent rather than treating it as a static policy file.
Delegate across frameworks to an A2A-enabled agentA2A connection.Agent-to-agent task contract, not just a generic HTTP endpoint.
Invoke a narrow service operationConnector, REST, MCP tool, or flow.No independent agent is needed for an ordinary operation.

Integrate Foundry, Fabric, and A2A deliberately

The Foundry-agent connection is Preview. Configure project connection, agent identity, and routing description. Current guidance requires the Activity endpoint; Responses/A2A endpoints alone do not satisfy it.

The Fabric data-agent connection is Preview. Select an accessible data agent, describe its analytical scope, and test source permissions. Connecting a specialist does not grant unrestricted data access.

A2A delegates agent tasks across frameworks. Configure the communication endpoint, authentication, and capability metadata. The message endpoint is not the card URL; MCP is the tool-exposure alternative.

Control routing, context, and completion

Define intent ownership, minimal context, completion, final formatting, and failure handling. Do not forward sensitive transcripts unnecessarily or let the parent claim success without a specialist result.

Test specialists independently, then ambiguous routing, missing context, unavailability, denied access, and misinformation across boundaries. Extra hops increase latency and governance; verify citations survive handoffs.

Lab 2.3 — Route a policy specialist without over-delegating
  1. Create a child agent for Northwind service policy if available in your authoring experience. Give it only the synthetic policy and instructions to refuse unsupported purchase authorization.
  2. Keep the request-status flow with the main agent. Describe the specialist as the place for policy explanations, not live ticket lookups. Test both intents and inspect the activity trace.
  3. Ask a mixed request: “Explain the policy and check NW-100.” Confirm each part reaches the appropriate capability and that the main response accurately separates policy from status.
  4. If child agents are unavailable, implement two clearly bounded topics with the same routing and context contract in the trial. This exercises decomposition but is not a completed multi-agent integration.
  5. Optionally connect a second Copilot Studio agent in an approved environment. For Foundry, Fabric, or A2A, first verify the required resource, identity, endpoint/protocol, and Preview status, then run one harmless delegated question if those resources exist.
  6. Disable the specialist temporarily where supported and rerun its question. Verify an honest fallback rather than a fabricated specialist answer.

Success check: you can justify child versus connected boundaries, demonstrate routing in the available environment, and list the extra authentication, protocol, and evaluation checks required for each external specialist.

Exam tip

Independent team, separate publishing, or independent ALM points toward a connected agent. Local organization inside one agent points toward a child. Cross-framework agent task delegation points toward A2A, not MCP.

Trap

Do not assume every connected type supports every topic redirect or channel. The current overview documents restrictions for Fabric data agents, including no explicit topic redirect. Check the target integration, not the general multi-agent concept.

Did you know?

A topic can redirect to a supported child or connected agent and then resume after that agent completes. Delegation can be one controlled step in a larger authored process rather than an irreversible transfer.

2.4 Integrate agents with Azure

Separate Search retrieval, model generation, and Application Insights observation. A model endpoint is not an index; telemetry is not knowledge; selecting a prompt model is not connecting a Foundry agent.

Understand the retrieval-augmented generation chain

RAG retrieves passages for generation. Preparation, chunks, embeddings, ranking, prompt instructions, and citations affect quality. A larger generator cannot repair an index missing the answer.

Azure OpenAI on your data for generative answers is Preview. Configure its documented Classic data connection through the topic node. Distinguish direct Search knowledge and Foundry-agent delegation.

Align Search index, model deployment, region, permissions, and source URLs. Verify both retrieval access and citation destination access; deployment existence does not prove the configured connection works.

Configure custom prompts with Foundry models

Connect a compatible Foundry deployment in prompt builder, supply exact deployment/base names, select it, and test. A catalog listing alone does not prove endpoint, region, capability, or policy compatibility.

The documented prompt BYOM path requires chat completions, not Responses, and excludes GPT-5-family/later models. Managed prompt model choices have different support; do not generalize these exclusions.

Compare grounding, schema adherence, latency, cost, input types, and responsible AI behavior. Lower temperature where supported reduces variability, not uncertainty or hallucination guarantees.

Observe through Application Insights without overcollecting

Configure the documented Application Insights connection string. Review logging switches before capturing conversation text or sensitive fields. Telemetry needs access, retention, privacy, and cost controls.

Use Kusto time windows, events, channel, and dimensions to diagnose symptoms. Exclude design-mode traffic for production metrics. Anonymous IDs do not reliably count people; reproduce failures with tests.

Lab 2.4 — Separate retrieval, generation, and observability
  1. In the trial agent, create a policy-answer topic using the synthetic document and a separate prompt that summarizes supplied incident facts, if prompts are enabled. Verify that changing the prompt does not change the stored policy.
  2. Create a small test matrix: answerable policy question, missing policy question, malformed request ID, and failed lookup. Record the expected retrieval, tool, and final-response outcomes.
  3. If an approved Foundry deployment is available, connect a supported chat-completions model in prompt builder, select it for the custom prompt, and rerun the same input cases. Record deployment and model identifiers without exporting secrets.
  4. If Search and Foundry on-your-data resources are available, configure the documented Preview generative answers connection and inspect actual citations. Otherwise diagram the question-to-index-to-model-to-citation flow and mark it as a design exercise.
  5. If Application Insights is available, configure the agent's connection, keep sensitive logging off unless explicitly approved, run synthetic test conversations, and inspect relevant custom events. Identify test traffic before interpreting usage.
  6. Without Azure resources, inspect test-chat activity and flow test outputs for the same matrix. State clearly that these are local diagnostics, not Application Insights telemetry.

Success check: you can assign each symptom to retrieval, model/prompt, integration, or telemetry; compare outputs using fixed cases; and identify which Azure integrations were actually exercised.

Exam tip

If the task is “use a different model for this prompt,” choose prompt model configuration. If it is “ask a specialist agent,” choose agent integration. If it is “find why deployed requests fail,” choose runtime telemetry plus reproduction.

Trap

Logging all conversation details is not automatically the best troubleshooting answer. Start with minimum necessary diagnostics, review sensitive-data exposure, and limit access and retention.

Did you know?

Application Insights agent telemetry also records test conversations. The documented designMode custom dimension lets queries distinguish test-pane activity from production activity.

Domain 3 — Test and manage agents (20–25%)

Evaluate behavior against explicit expectations, then move the same governed solution through its lifecycle. Quality depends on tests, identities, configuration, and external dependencies as much as the prompt itself.

3.1 Evaluate agent performance

A test set holds repeatable inputs and expectations; the method defines correctness. Telemetry records runtime behavior. Successful execution alone proves neither answer accuracy nor appropriate behavior.

Build representative tests, not just easy questions

Cover intents, paraphrases, missing data, unsupported requests, denied access, conflicting sources, dependency failures, and required refusal. Keep a stable regression set; generated cases may miss knowledge gaps.

Create single-response sets manually, by import, or generation. They test independent questions. Use conversation tests for context, clarification, and interruptions; single-turn success cannot prove multi-turn correctness.

Lab 3.1 — Evaluate policy answers, tool use, and refusal
  1. Create six synthetic test cases: a policy question, its paraphrase, an unsupported policy question, NW-100 lookup, unknown-ID lookup, and a purchase-approval request. State the expected outcome for each.
  2. Create a single-response test set manually or import a file using the current product template. Use compare meaning for policy, tool use for lookup, and a custom method for required refusal where available.
  3. Supply each method's required expectations. Review the active user and connections before running; use no production data.
  4. Run the set and inspect every failure or invalid result. Confirm that the lookup used the intended tool and that its final answer matches the returned status.
  5. Change one tool description or prompt, rerun the same set, and compare case-level results. Do not replace hard cases to inflate the score.
  6. Add a manual multi-turn test: ask a policy question, then a short follow-up referring to “that rule.” Use conversation evaluation if available; otherwise record the manual trace separately.

Success check: you can justify each method, distinguish invalid configuration from incorrect behavior, and show a reproducible before/after comparison without confusing local evaluation scores with exam scores.

Exam tip

“Equivalent meaning” suggests compare meaning, “same exact string” suggests exact match, and “used the required capability” suggests tool use. An expected refusal calls for a rubric that rewards refusal.

Trap

A high average can hide a critical unauthorized action or fabricated approval. Review safety-critical cases individually and keep release criteria separate from a convenient aggregate score.

Did you know?

You can populate a test set from test-chat questions. That turns a useful manual investigation into a repeatable regression check, provided you add the right expectations and review sensitive content.

3.2 Implement ALM for agents in Copilot Studio

ALM moves versioned components and configuration through environments. Publishing updates runtime; solution transport moves application components. Manual reconstruction creates drift.

Package components and resolve dependencies

Create a custom solution with publisher, agent, flows, connection references, connectors, and variable definitions as needed. Check dependencies. Table definitions can move in solutions; business records do not move automatically.

Develop in unmanaged solutions; govern downstream managed deployment. Avoid ad hoc production edits and unmanaged layers. Align source history, versions, tests, and ownership with the release artifact.

Separate configuration from implementation

Environment variables separate configuration from logic. Definitions can include defaults; current values take precedence. Supply target values deliberately so development endpoints do not leak into production.

Bind connection references to authorized target connections. They do not eliminate ownership, consent, or authentication. Use supported secret storage, never plain-text credential variables; verify components consume the intended configuration.

Implement and extend pipelines

Pipelines validates dependencies and target connections/variables before deployment. The same exported artifact progresses through stages, while approved environment configuration can vary.

Governed extensions support pre-export checks, delegated deployment, and pre-deployment gates. Subscribe to documented Dataverse events and report completion/rejection. Unanswered gates remain pending; personal pipelines cannot be extended.

Check pipeline host, roles, licensing, and Managed Environment requirements. A trial does not guarantee pipeline deployment rights. Provision external Azure resources separately; solution transport does not clone them.

Lab 3.2 — Package configuration without environment drift
  1. In an environment where solution authoring is permitted, create a custom Northwind Study solution and add your existing agent and related agent flow. Review required dependencies rather than selecting every unrelated component.
  2. Create a text environment variable for a synthetic support URL. Set a clearly nonproduction default/current value and reference it in a supported flow action or message-building step.
  3. Run the agent and verify the configured value is used. Change the current value and rerun the dependent component using the product's supported save/publish steps. Confirm which value takes precedence.
  4. Review connection references and prepare a deployment checklist: target connections, variable values, source access, external resources, authentication, and channel validation.
  5. If export and a second approved environment are available, transport the solution, supply target settings, and rerun the Lab 3.1 cases. Otherwise inspect solution components and document the intended import inputs without claiming a deployed result.
  6. If an administrator has configured a governed pipeline, validate and deploy to a nonproduction stage. For extension study, design a pre-deployment approval that records its outcome and completes/rejects the gate; implement only where authorized.

Success check: the agent and flow are visible in the custom solution, configuration is separated from logic, and the target checklist includes connections and external resources. Any optional deployment is followed by behavior tests, not just an import-success message.

Exam tip

A varying endpoint belongs in environment configuration; a live conversation answer belongs in a topic variable; a target credential binding belongs in connection configuration. Match the lifecycle of the value to the mechanism.

Trap

A solution import succeeding does not prove that the target agent is published, its connections are authorized, its sources are accessible, or its external models exist. Treat deployment and operational validation as separate checks.

Did you know?

Pipelines preserve the exported release artifact as it advances through stages. Editing development after a deployment request does not mean later stages automatically receive those new edits.

Common traps
  • Grounding is not training: knowledge supplies retrieval context, not foundation-model retraining.
  • Knowledge is not action: confirm writes through authoritative tool results.
  • Sign-in is not authorization: inspect conversation identity, connection identity, and source access separately.
  • Prompts are not enforcement: retain data policies and transaction controls.
  • Fixed flows can contain variable AI: explicit order does not make every output deterministic.
  • MCP is not A2A: tool exposure differs from agent delegation and protocol-specific integration.
  • Trial is not deployment entitlement: test chat does not grant publishing or every premium service.
  • Preview is integration-specific: distinguish feature, model, and product maturity.
  • Telemetry is not evaluation: execution success does not prove accurate meaning or appropriate refusal.
  • Practice percentages are not official scaled scores: no published AB-620 conversion formula exists.
